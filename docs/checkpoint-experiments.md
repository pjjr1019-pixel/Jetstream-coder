# Checkpoint and exclusive-write experiments

Checkpoint preparation and inspection are available for approved candidates; they do not modify project files. The write, rollback and journal fixtures are not connected to a production Apply path and must not be used for real projects.

The app's current Apply/recovery/rollback routes are restricted to disposable temp projects and app-data directories. On project reopen, recorded checkpoints are reinspected: unresolved or unreadable checkpoints are recorded in job history and keep the job blocked, duplicate warnings are not repeated, and status is reconciled only after all of that job's checkpoints inspect clean. Explicit recovery is conflict-aware and never restores over bytes that differ from the checkpoint's recorded after-state. This is tested prototype behavior, not production Apply authorization.

`checkpoint.ts` prepares and inspects a single-file checkpoint, `exclusive-write.ts` tests an exclusive Windows compare-and-write, and `checkpoint-journal.ts` validates an append-only state sequence. `checkpoint-fixture.ts` combines them only for disposable tests.

The renderer reports unsaved editor paths to the main process, which blocks candidate approval and checkpoint preparation when editor state is unknown or dirty. This does not protect an Apply transaction; no production Apply path exists. Remaining production-safety work includes preventing all target-path substitution and reparse-point races, establishing durable ordering (including power-loss behavior), recovering safely after a process dies during an in-place write, binding trusted production approval evidence to an Apply boundary, preserving editor-state protection through any future Apply transaction, and running post-apply checks on a production-authorized path. A thrown test callback is not a real process-termination or power-loss test. Production Apply remains disabled until those requirements are met and verified.
