# Tunnel recovery — staged operator procedure

This is a draft for the staged candidate, not an instruction to change the live VM. Until the candidate has been independently verified and approved, do not install or run it against live tunnel state. `tunnel_operator.py` inspects metadata; it does not read or print chat text, authenticate to the agent, signal processes, retry a turn, or delete files.

1. Run `python3 tunnel_operator.py --work-dir /absolute/path/to/tunnel-state status` in the approved environment. A claimed turn older than 300 seconds is `outcome_uncertain`; a reply conflict, dead-letter or retained cleanup item is `review_required`. A recent claim does not establish that a worker is alive. A `reply_accepted` state means the agent provided a matching receipt; it does not prove the phone displayed the reply. Check `unrecognized_file_counts`: nonzero means the report has omitted an unsupported identifier and an operator must inspect it safely. The report is a snapshot and can change immediately.
2. Check the app's history and Muse conversation for that exact turn before deciding what happened. A missing result is not proof that work did not run. A worker may still be active, and PC actions may have occurred even when no reply exists. Do not rerun the turn automatically.
3. Record the human review only when needed: `python3 tunnel_operator.py --work-dir /absolute/path/to/tunnel-state record-review --turn-id TURN_ID --outcome unknown --confirm-turn-id TURN_ID`. Allowed outcomes are `unknown`, `waiting`, `not_sent_after_review`, and `completed_elsewhere`. The latter two are the operator's assertion, not a transport guarantee. Confirmation must match the exact ID. Notes do not change turn ownership, deliver a reply, clear a duplicate guard, or authorize a retry; they contain no message text. A later manual retry requires checking the app's warning and remains the user's decision.
4. For a stale heartbeat with a live PID, the supervisor intentionally does **not** kill it because the PID could have been reused. The report labels every PID `identity_unverified`. An operator must separately verify the process, its ownership, and the state of in-flight work before taking any action. Do not kill by name, delete a PID file as a substitute for identity verification, or start a competing loop. If the loop has exited, the supervisor's normal missing-loop path can start it.
5. Resolve retained conflicts and dead-lettered files only after correlating the original turn and the agent's stored receipt. Preserve evidence. The CLI deliberately provides no bulk delete, replay, or process-kill operation.

Completion markers and turn fingerprints are retained indefinitely. This is intentionally unbounded: no age alone proves that an old worker stopped or that a turn ID cannot be replayed. The status command reports their counts. Monitor available storage; do not prune these files until a separately reviewed archival/retention procedure can preserve duplicate suppression and cleanup evidence.

## Explicit removal of a reviewed claim

Use this only after the staged candidate has passed verification and has been approved for the intended environment. First inspect the exact turn ID, preserve any evidence needed for the review, and verify the identity and termination of **every worker that might still be handling that turn**. A matching reply receipt proves that a reply was accepted; it does **not** prove that a worker has stopped or that its actions have finished. If worker identity or activity is uncertain, leave the claim in place and seek further review.

After that review, the operator may explicitly authorize removal of that one matching claim with `python3 inbox_cleanup.py --claim-reviewed /absolute/path/to/tunnel-state TURN_ID`. This is a file-removal operation, not a retry or a stop command. The helper checks the original turn fingerprint and completion receipt; an `unverified`, `conflict`, or `retained` result means the file was not safely removed and needs investigation. Never treat an absent or failed check as permission to delete the claim manually.

If cleanup is interrupted after capturing a file, `python3 inbox_cleanup.py --sweep /absolute/path/to/tunnel-state` can finish an earlier authorized removal. The staged hook also runs this sweep automatically. Consequently, a file already captured by an explicit `--claim-reviewed` operation may be removed by a later sweep without a second prompt: perform the worker and evidence checks **before** the original authorization, not merely before a manual sweep. The sweep also processes captured ordinary inbox-cleanup items, and preserves captures that fail evidence checks. Review retained conflicts; do not remove them blindly.

This workflow exposes and documents uncertainty; it does **not** automatically resume a turn whose initial wake was lost, clear cleanup backlogs, or guarantee that Muse performed no action. Those decisions require an operator and, where applicable, user confirmation.
